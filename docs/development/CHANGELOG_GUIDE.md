# Правила ведения CHANGELOG

Этот документ задаёт канонический формат `CHANGELOG.md` для ZeTer Photo Editor.

## 1. Что считается опубликованным

Для журнала изменений состояние, уже слитое в ветку `main`, считается **актуальным опубликованным состоянием репозитория**.

Поэтому:

- не создавай и не сохраняй раздел `Unreleased` для изменений, которые уже находятся в `main`;
- после merge запись должна находиться в верхнем разделе текущей версии;
- открытый PR, рабочая ветка или локальные изменения ещё не считаются опубликованными и в канонический `CHANGELOG.md` основной ветки не попадают;
- публикация в `main` не равна автоматическому deploy внешнего сайта. Состояние сайта/хостинга проверяется и документируется отдельно, если задача касается deployment.

## 2. Язык

Обычный текст и заголовки новых записей веди **на русском языке**.

Английский оставляй там, где он точнее и является техническим именем или устоявшимся термином, например:

- `Smart Object`, `Content-Aware Fill`, `live target`, `rollback`, `fallback`;
- имена API, классов, функций, файлов, форматов и полей;
- команды `npm run check`, `git diff --check`;
- названия технологий, форматов и продуктов: PSD/PSB, Canvas, WebGPU, GitHub Actions;
- точные тексты идентификаторов, путей и кодовых сущностей.

Не пиши обычные описательные предложения на английском только потому, что старые записи так оформлены. Старые англоязычные записи считаются legacy и не являются примером стиля для новых изменений.

## 3. Структура версий

Верхний раздел соответствует версии из `package.json`:

```md
## 1.42.0 — текущая версия
```

Пока версия в `package.json` не меняется, новые слитые в `main` изменения добавляй в этот же верхний раздел.

При реальном bump версии:

1. у прежнего раздела убери пометку «текущая версия» и зафиксируй дату завершения, если она известна;
2. создай новый верхний раздел с новой версией из `package.json`;
3. не создавай промежуточный `Unreleased`, если изменение уже слито в `main`.

Не придумывай версию, которой нет в `package.json`.

## 4. Формат записи

Предпочтительный формат:

```md
### 2026-10-07T20:09:52+03:00 — Проверена актуальная membership Smart Object

- Добавлено: ...
- Исправлено: ...
- Изменено: ...
- Проверено: ...
- Ограничения проверки: ...
```

Если точное время не нужно или неизвестно, допустим `YYYY-MM-DD`.

Заголовок должен кратко говорить, что реально изменилось. Не используй английский заголовок для обычного описания, если это не точное имя функции/технологии.

## 5. Допустимые метки

Для обычного текста используй русские метки:

- `Добавлено:`
- `Изменено:`
- `Исправлено:`
- `Проверено:`
- `Документация:`
- `Ограничения проверки:`
- `Совместимость:`
- `Безопасность:`

Технические слова внутри пункта можно оставлять на английском.

## 6. Что записывать

Записывай только фактические изменения, уже присутствующие в `main`:

- пользовательские функции;
- исправления багов;
- изменения архитектуры, которые важны для сопровождения;
- совместимость форматов;
- значимые reliability/safety изменения;
- тесты и проверки, если они фиксируют важный контракт;
- существенные изменения документации и процесса разработки.

Для source change укажи проверку, которая реально выполнялась. Если слой проверки не запускался, не маскируй это формулировкой «всё проверено».

## 7. Чего не записывать как готовый результат

Не выдавай за выполненное:

- планы и будущие задачи;
- содержимое `task/`, которое ещё не реализовано;
- открытый PR до merge;
- ожидающий или упавший CI;
- неподтверждённую гипотезу как исправленный баг;
- поддержку формата/браузера/режима, которую не проверяли.

Если гипотеза важна для продолжения, храни её в `task/`, а не в разделе готовых изменений.

## 8. Порядок записей

Внутри текущей версии держи новые записи сверху, в обратном хронологическом порядке.

Если поздняя правка была вставлена ниже более старой записи, исправь порядок вместо того, чтобы оставлять журнал несортированным.

## 9. Исторические legacy-записи

Не делай массовый шумовой rewrite всей старой истории только ради перевода.

При касании старой записи можно перевести её обычный текст на русский, сохранив технические термины и фактический смысл. Все новые записи обязаны сразу соответствовать текущему русскоязычному формату.

## 10. Проверка перед merge

Перед завершением изменения changelog проверь:

- текущую версию в `package.json`;
- отсутствие `## Unreleased` для уже слитого состояния;
- русский язык обычного текста новых записей;
- правильный обратный хронологический порядок;
- отсутствие планов, неподтверждённых заявлений и выдуманных проверок;
- соответствие фактическому diff/commit/CI;
- `git diff --check`.

Для изменений, затрагивающих source/runtime, действуют обычные gates из `docs/development/QUALITY_PLAYBOOK.md` и `docs/testing/TEST_MATRIX.md`.
