# 064 — Восстановление autosave после временного отказа хранилища

- Приоритет: P2 (reliability).
- Статус: ожидает PR CI и интеграции.
- Исходная ветка: `main@95a0c57cea427389d33d683c9002d16bf45b14fd`; рабочая ветка: `quality/recovery-retry-064`.
- Найденная первопричина: `reportRecoveryFailure()` безусловно выставлял `recoveryStorageAvailable=false`, а `queueRecovery()` всегда выходил при этом состоянии. Даже когда следующий `storage.save()` мог успешно выполниться, нового обращения не происходило до reload.
- Контракт исправления: только отказ **записи autosave** допускает повтор при последующем событии queue, не раньше чем через 30 секунд; таймеры самостоятельных retry не создаются. Успех публикует восстановившуюся доступность. Последовательные операции повторно проверяют cooldown после предыдущего await.
- Безопасность: провал `loadAll()` на старте и ошибка `renameRecovery()` не разрешают autosave, потому что содержимое собственного window key могло остаться непрочитанным; записи другого ключа не трогаются.
- Проверки: добавлены deterministic tests на восстановление после первого rejection, свежий снимок, чужой ключ, постоянный отказ без retry storm и read-failure lockout. На момент подготовки commit CI ещё не подтверждён.
- После успешных PR CI, merge и точного `main` push CI удалить эту карточку; результат останется в `CHANGELOG.md` и test matrix.
